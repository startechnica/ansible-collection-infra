# Design: Percona Backup for MongoDB (PBM) — sharded-cluster PITR

Status: **implemented** (Phases 1–3 landed in 1.0.3 / `fix/walg`) — **needs
validation against a live sharded cluster** before it's declared production-ready.
Target: 1.0.3
Author: scoped during 1.0.3 prep

> Implementation notes vs. this design: agents are managed entirely in
> `roles/mongodb/tasks/pbm.yml` (runs after `init_cluster.yml`) rather than woven
> into the main stack templates — Quadlet units on podman, standalone
> `docker run` containers on docker — so auth/user creation is sequenced before
> the agents start. NetBox registration (O2) was skipped: agents expose no
> listening port. A single parameterized Quadlet template
> (`quadlets/mongodb-pbm.container.j2`) covers both the shard and config agents.

## Why

The role's current backup path is `mongodump` run through a throwaway container
that connects to **mongos**. That gives us full/scheduled logical backups and a
scratch-restore/verify flow. It does **not** give us point-in-time recovery on a
**sharded** cluster, because:

- `mongodump --oplog` is rejected against a `mongos` (only valid against a
  `mongod` replica-set member or standalone). Hence `mongodb_backup_pitr`
  defaults to `false` and is documented as replica-set-only.
- Consistent PITR across shards needs **coordinated per-shard oplog capture**
  with the balancer stopped — impossible to assemble from a single mongos dump.

[Percona Backup for MongoDB](https://docs.percona.com/percona-backup-mongodb/)
(PBM) is the standard tool for exactly this. It runs an agent next to every
data-bearing `mongod`, reads each replica set's oplog **directly from the
mongod** (never via mongos), continuously slices it to object storage, and
coordinates cluster-consistent snapshots + `pbm restore --time=...`.

## Hard constraint: Community MongoDB ⇒ logical backups only

This collection deploys the **Community** `docker.io/mongo` image. PBM's
**physical** backups/restores require the `$backupCursor` aggregation stage,
which exists only in **Percona Server for MongoDB (PSMDB)** and MongoDB
Enterprise — *not* Community.

**Therefore, on the current image, PBM gives us:**
- ✅ Logical backups (BSON, mongodump-equivalent) — cluster-consistent across shards
- ✅ **Logical PITR** (continuous oplog slicing → restore to a timestamp)
- ❌ Physical backups / fast physical restore (would require switching the
  cluster image to `percona/percona-server-mongodb`)

Logical PITR is the feature we actually want, so Community is sufficient — but
this constraint must be stated in docs, and "switch to PSMDB" is the upgrade
path if physical backups are ever needed. **Open question O1** below.

## PBM architecture, mapped to this collection's topology

PBM requires **one `pbm-agent` per `mongod` process** that belongs to a replica
set being backed up. In this collection every host co-locates a shard `mongod`,
a `configsvr` `mongod`, and a `mongos` (sharded mode). So:

| Cluster type | Agents per host | Connects to |
|---|---|---|
| `sharded` | **2** | local shard `mongod` (`rs0`, port `mongodb_mongod_node_port`) **and** local `configsvr` (`configReplSet`, port `mongodb_configsvr_node_port`) |
| `replicaset` | **1** | local `mongod` (`rs0`, port `mongodb_mongod_node_port`) |

- **No agent on mongos** — mongos is a router, has no oplog. PBM commands are
  *issued* against the cluster (via any mongod / the config RS), but the agents
  live on the data nodes.
- A 3-node sharded cluster ⇒ **6 agents** (3 shard + 3 config). Each agent is a
  small sidecar container alongside the `mongod` it manages.

This is the single biggest structural difference from the exporter sidecar
(which is one-per-host): PBM is **two-per-host** in sharded mode, each pinned to
a different local mongod port.

## Authentication (reuse the existing X.509 PKI)

Follow the healthcheck/exporter client-cert pattern exactly:

1. **New client cert** `pbm-agent.pem`, subject
   `CN={{ mongodb_pbm_cn }},OU={{ mongodb_pki_client_ou }},O={{ mongodb_pki_o }}`
   (default CN `mongodb-pbm`), signed by the same CA, distributed to
   `{{ mongodb_tls_dir }}/pbm-agent.pem` (mode 0400, owner mongodb:mongodb).
   Generated by the existing `_generate_client_cert.yml` helper.
2. **`$external` user** mapped to that DN, created during `init_cluster.yml`
   (same place healthcheck/exporter users are created), granted PBM's required
   privileges. PBM documents a role set; we create a `pbmAnyAction`-style custom
   role (readWrite on PBM control collections + backup/restore/clusterMonitor +
   oplog read). Exact grants pinned to the PBM version we ship.
3. Each agent's `PBM_MONGODB_URI` →
   `mongodb://localhost:<local mongod port>/?authMechanism=MONGODB-X509&authSource=$external&tls=true&tlsCertificateKeyFile=/etc/mongo/ssl/pbm-agent.pem&tlsCAFile=/etc/mongo/ssl/ca.pem&directConnection=true`
   (`directConnection=true` so the agent talks to *its* node, not whoever's
   primary).

No new secrets: the agent authenticates by cert, like the exporter.

## Storage config (reuse `s3_*`, but via PBM-native S3 — not mc)

PBM has **native** S3 support; we do **not** use the `minio/mc` path. PBM config
is stored *in the cluster* and applied once with `pbm config --file`. Rendered
from the existing shared vars:

```yaml
storage:
  type: s3
  s3:
    region: "{{ s3_region }}"
    endpointUrl: "{{ s3_endpoint }}"
    bucket: "{{ s3_bucket }}"
    prefix: "{{ s3_prefix }}/pbm"        # namespaced under the existing prefix
    credentials:
      access-key-id: "{{ s3_access_key }}"
      secret-access-key: "{{ s3_secret_key }}"
pitr:
  enabled: "{{ mongodb_backup_pitr | bool }}"
  compression: "{{ mongodb_pbm_compression }}"
```

Note PBM uses the AWS SDK (sigv4); the digit-leading-key / URL-encoding issues we
hit with `mc` don't apply here — credentials are passed as discrete fields, not
spliced into a URL.

## Deployment (respect `mongodb_container_engine`)

Mirror the exporter sidecar wiring across both engines:

- **Podman / Quadlet** (`Network=host`): two new templates
  `quadlets/mongodb-pbm-shard.container.j2` and
  `quadlets/mongodb-pbm-config.container.j2` (config one rendered only when
  sharded). `After=`/`Wants=` the corresponding mongod/configsvr unit. Image
  `mongodb_pbm_image`, `User=` mongodb uid/gid, the `pbm-agent.pem`+`ca.pem`
  volumes, `PBM_MONGODB_URI` env, `Memory={{ mongodb_pbm_mem_limit_mb }}m`.
- **Docker Compose**: two new services with
  `network_mode: service:mongod` and `network_mode: service:configsvr`
  respectively, so each agent shares its target mongod's netns and reaches it on
  `localhost`.

PBM agents are stateless (state lives in the cluster + S3), so no data volumes.

## New variables (`mongodb_pbm_*`)

```yaml
mongodb_pbm_enabled: false                 # master switch
mongodb_pbm_image: "percona/percona-backup-mongodb:2.x.y"   # pin, not :latest
mongodb_pbm_cn: "mongodb-pbm"              # client-cert CN
mongodb_pbm_mem_limit_mb: 256
mongodb_backup_pitr: false                 # enable continuous oplog slicing (shared knob)
mongodb_pbm_compression: zstd              # none|gzip|snappy|lz4|s2|zstd
mongodb_pbm_compression_level: ""          # optional codec level (zstd 1–22, …)
mongodb_pbm_init_backup: true              # base backup on provision (PITR anchor)
```

Scheduling + retention reuse the **shared backup knobs** rather than PBM-specific
ones: the timer fires on `mongodb_backup_schedule` (empty disables it) and a
post-backup `pbm cleanup` prunes base backups + their oplog chunks older than
`mongodb_backup_retain_days`. One schedule, one retention window, for both the
mongodump path and PBM.

S3 target is the existing `s3_*` set — no duplication.

## Tasks & action dispatch

Add to `roles/mongodb/tasks/`:

- `pbm.yml` — render agent units (engine dispatch), apply `pbm config` once,
  enable PITR if requested, start agents. Included from `main.yml` during
  `provision` when `mongodb_pbm_enabled`. Idempotent: `pbm config` is declarative.
- Extend `init_cluster.yml` — create the `$external` PBM user + role.
- Extend `certificates.yml` — emit `pbm-agent.pem` when `mongodb_pbm_enabled`.
- Extend `uninstall.yml` — stop/remove agent units + cert.

New `mongodb_action` values routed in `main.yml` (thin wrappers over the `pbm`
CLI, run once via `_container_exec` against any agent):

- `pbm-backup` → `pbm backup --compression=…`
- `pbm-restore` → `pbm restore <name>` or `pbm restore --time='YYYY-MM-DDThh:mm:ss'`
- `pbm-status` → `pbm status` (+ `pbm list`)

## Day-2 playbooks (`playbooks/mongodb/`)

- `pbm-backup.yml` — trigger a PBM backup, wait for completion, report.
- `pbm-restore.yml` — `-e pbm_target='2026-06-09T12:00:00'` or `-e pbm_backup=<name>`;
  guard-railed (stops balancer is automatic; warns it's cluster-wide and
  disruptive — restore requires no active writes / app downtime).
- `mongodb_pbm_status.yml` (playbooks root, FQCN-addressable) — show agents, storage, PITR window, backup list.

Unlike the mongodump `pitr.yml` scratch-restore, **PBM restore is whole-cluster
and in-place** — there's no "inspect in a scratch container" mode. That's a
documented operational difference, not a gap.

## NetBox / firewall

- Add a `pbm-agent` entry to `_mongodb_services_*` in `vars/main.yml` so the
  port (if we expose one) registers. **Caveat:** PBM agents don't *listen* on a
  port — they're outbound (to mongod + S3). So there may be **nothing to
  register or firewall**. Likely a no-op; confirm during implementation
  (**O2**).

## Coexistence with the existing mongodump backup

Both can run. Guidance to document:

| Need | Use |
|---|---|
| Replica-set PITR, scratch-restore/inspect single DB | existing `mongodump` + `pitr.yml` (`mongodb_backup_pitr: true`) |
| **Sharded** cluster-consistent backup + PITR | **PBM** (`mongodb_pbm_enabled: true`, `mongodb_backup_pitr: true`) |
| Quick ad-hoc logical dump of one DB to S3 | existing `mongodump` |

Recommend **not** enabling both PITR mechanisms on the same cluster
simultaneously (two oplog consumers = wasted IO + confusing recovery story).
On sharded clusters, PBM is the answer and `mongodb_backup_pitr` stays false.

## Phased implementation

1. **Phase 1 — agents + config (no PITR):** cert, `$external` user/role,
   Quadlet + compose templates, `pbm.yml`, `pbm config` apply, `pbm-status`.
   Validate `pbm status` shows all agents green and storage reachable.
2. **Phase 2 — backups:** `pbm-backup.yml`, `mongodb_action: pbm-backup`,
   scheduled timer + `pbm cleanup` retention via the shared
   `mongodb_backup_schedule` / `mongodb_backup_retain_days` knobs (reuse the
   systemd-timer pattern from `backup_schedule.yml`).
3. **Phase 3 — PITR + restore:** `mongodb_backup_pitr`, `pbm-restore.yml`,
   restore-to-timestamp, retention (`pbm delete` / retention policy).
4. **Phase 4 — docs:** role README section, UPGRADING note, decision table
   above, the Community-vs-PSMDB constraint.
